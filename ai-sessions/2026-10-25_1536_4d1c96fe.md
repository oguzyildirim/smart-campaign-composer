# Scheduled campaign delivery: analysis

I read the approval path, the state machine, both migrations, and the worker loops. I haven't changed any code.

## Where scheduling hooks in

Today approval and queueing happen in one transaction (`campaign.Service.Approve` → `CampaignStore.Update` → `materializeDeliveries`):
- It re-checks the content hash and rule.
- It compiles the segment with `now` (`segment.Compile(c.Rule, now)`), so "last 30 days" is measured from the approval time.
- It checks content lengths against the real audience, inserts the deliveries, and writes outbox rows.
- The outbox relay publishes to Kafka right away.

Scheduling puts a delay between "a human approved" and "deliveries exist or are claimable".

**Don't just set a future `next_attempt_at` at approval.** It looks like a one-line fix but it loses messages:
- `Claim` only takes rows with `next_attempt_at <= clock_timestamp()` (`deliveries.go:74`).
- The outbox would still publish immediately.
- The claim would fail, and `Process` treats a failed claim as a duplicate and drops it (`processor.go:66`).
- `RequeueDue` only picks up `status = 'retrying'`.

Every delivery would be stranded in `queued`.

## The main choice: when the audience is built

| | **A. Build at approval, hold until due** | **B. Approve now, build at the scheduled time** |
|---|---|---|
| Recipients | Fixed when approved | Fresh when sent |
| "Last 30 days" measured from | Approval time | Send time (what the marketer means) |
| Approval checks (longest real first name, ≥1 recipient) | Still cover the exact recipients | Must run again at send time with no human present, so they can fail |
| Cancel or reschedule | Must delete or cancel thousands of rows; deliveries need a `canceled` status | Easy: nothing has been created yet |
| Plumbing | Hold the outbox rows (a new delivery status or an outbox `available_at`), and change claim and maintenance code | Reuses `materializeDeliveries` unchanged |
| Consent | Checked again before each send (already in place) | Checked when the audience is built and again before each send |

**I recommend B.** It matches what the marketer means by "send this Friday morning". It keeps the delivery and outbox code unchanged and makes cancelling trivial. Its one real cost is that the audience checks run without a human. That's acceptable because those checks already exist as code and per-recipient rendering is still the final safeguard. When a check fails, the campaign needs a clear failure state rather than being sent anyway.

## Design sketch for B

**State machine**
```
drafts_ready ──approve(scheduled_at)──▶ scheduled ──release (system)──▶ approved → sending → completed
                                         │  ▲
                                cancel ──┘  └── (back to drafts_ready, approval cleared, version++)
scheduled ──release checks fail──▶ release_failed   (needs a human: cancel and re-approve)
```
- `Approved()` must include `scheduled`, so content stays locked and the content hash still binds it.
- Approving without `scheduled_at` keeps today's behaviour exactly.
- Migration: update the status and approval constraints and the event actions (`scheduled`, `released`, `schedule_canceled`, `release_failed`). Add `scheduled_at timestamptz` with `CHECK ((status='scheduled') = (scheduled_at IS NOT NULL))`, or keep it for the audit trail. Add a partial index `ON campaigns (scheduled_at) WHERE status = 'scheduled'`.

**Release (domain logic in `internal/campaign`)**
- `Service.Release(ctx, id)` runs the existing approval checks minus the human input: rule revalidation, content validation, `inspect`, and at least one recipient. It then returns a `Write` with a `DeliveryPlan`. Factor the shared part out of `Approve` rather than copying it.
- A due campaign that is no longer `scheduled` is a no-op. With the `FOR UPDATE` lock, this makes release idempotent across workers.
- Compile the segment with the scheduled time, not wall-clock `now`. A late release then uses the same window the marketer intended.

**Trigger (worker)**
- Add a task to `RunMaintenance` that finds due campaigns using the database clock (`scheduled_at <= clock_timestamp()`, `FOR UPDATE SKIP LOCKED`, limited batch) and calls `Release`.
- This means the worker depends on `campaign.Service`; that's a wiring change in `cmd/worker`.
- Timing precision is `DELIVERY_SCAN_INTERVAL`, so the README should say "sent within one interval after the scheduled time".
- If the worker is down at the scheduled time, the campaign is sent late when it comes back. That's a choice: alternatively, mark it expired after a grace period. I'd send late and record the lateness in the event.

**Input rules**
- RFC3339 timestamp with a required offset; store it as `timestamptz`.
- Must be in the future, allowing a small margin for clock skew.
- Maximum horizon, e.g. 30 days.
- The UI shows Europe/Istanbul local time, but the backend validates.

**Unchanged:** the rate limit (a large release just drains at 100/s through the shared bucket), idempotency, retries, and the consent check before each send.

**Monitoring:** progress and SSE show `scheduled` with `scheduled_at`. A `release_failed` campaign shows the error codes. Add metrics for campaigns released or failed and for release lateness.

**Tests**
- Unit tests with a fake clock:
  - a past or too-far time is rejected
  - release before the due time does nothing
  - release after the due time builds the deliveries
  - cancel and then re-approve works
  - a release-time check failure leads to `release_failed`
  - an approval request with the wrong content hash is rejected
- Integration tests:
  - two workers releasing at once create one set of deliveries
  - a user whose consent is revoked between scheduling and release is excluded
  - a user who joins the segment is included
- End to end: schedule, release, and send through Kafka.

## Decisions for you

1. **Build the audience at approval (A) or at send time (B)?** I recommend B.
2. **Is cancel or unschedule in scope?** With B it's cheap, and it's the main reason a human-approval flow needs scheduling.
3. **If release is late (worker down):** send late, or expire after a grace period?
4. **On a release-time check failure:** a new `release_failed` status, or back to `drafts_ready` with the approval cleared? I prefer the explicit status because silently undoing an approval is surprising.

Once you've chosen, I can turn this into a milestone with acceptance criteria and start with the migration and the `campaign` domain changes.

# Milestone 8 — Scheduled campaign delivery

## Problem Statement

A marketer can only approve a campaign for immediate sending: approval creates every
delivery and queues it in the same transaction. They cannot say "send this Friday at
10:00", and once approved there is no way to stop a campaign before it goes out. A
naive delay (a future next_attempt_at on deliveries created at approval) would lose
messages: the outbox publishes at once, the claim refuses a delivery that is not due,
and the processor drops the job as a duplicate. Relative segment windows ("added to
cart in the last 30 days") would also be measured from approval time, not from when
the messages are actually sent.

## Solution

The marketer can approve a campaign for a future time. Approval still binds the exact
reviewed content (version + content hash) and records who approved it, but no
deliveries are created yet: the campaign is `scheduled`. At the scheduled time a worker
releases it: inside one transaction it re-runs every approval check against the
audience as it is then (segment compiled with the scheduled time as reference time),
creates the deliveries and outbox messages, and moves the campaign to `approved`, from
where sending works exactly as today.

fails, the campaign moves to `release_failed` with the reasons and sends nothing. If a
due campaign is not released within a grace period (e.g. workers were down), it moves to
`expired` and sends nothing. Approving without a scheduled time behaves exactly as
before.

- **Timing defaults:** a 15-minute grace period, scheduling at least 1 minute ahead, and at most 30 days ahead. Each is configurable, and the config check rejects a grace period shorter than `DELIVERY_SCAN_INTERVAL`.

- **New endpoints:** `POST /campaigns/{id}/reschedule` and `POST /campaigns/{id}/cancel`. Both take the version and content hash the marketer saw, plus the name of the person acting.
- **Live dashboard stream:** it closes for `expired` but stays open for `release_failed`, because a cancel may follow.
